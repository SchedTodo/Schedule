# Git 提交规范

本规范延续仓库历史中已有的 `feat`、`fix`、`refactor`、`build`、`style`、`docs` 风格，并从 Schedule v2 开始统一中文描述。

## 提交格式

```text
<类型>(可选范围): <中文祈使式描述>
```

示例：

```text
feat(parser): 增加日程语法诊断模型
fix(calendar): 修复跨时区事件日期偏移
refactor(electron): 拆分窗口与托盘生命周期
test(database): 覆盖 1.2 数据迁移幂等性
build: 升级 Vite 8 构建配置
docs: 补充平台适配器开发说明
```

## 允许的类型

- `feat`：新增用户功能、领域能力或公开接口。
- `fix`：修复缺陷或错误行为。
- `refactor`：不改变外部行为的结构调整。
- `test`：新增或调整测试，不改变生产行为。
- `build`：依赖、构建器、打包或生成流程。
- `ci`：持续集成、发布流水线。
- `docs`：文档和代码外说明。
- `style`：格式、样式或不影响逻辑的表现调整。
- `perf`：可验证的性能改进。
- `chore`：无法归入以上类型的仓库维护工作。

## 标题要求

- 类型使用小写英文，冒号后使用简体中文。
- 标题直接说明完成的结果，不使用“修改一下”“更新内容”等含糊表述。
- 标题末尾不加句号。
- 一个提交只包含一个可独立验证、可独立回滚的目的。
- 重大变更在正文中增加 `BREAKING CHANGE:`，说明影响和迁移方式。

## 范围建议

范围应使用稳定模块名，例如：

```text
web
parser
domain
contracts
database
electron
sync
calendar
settings
```

小型或跨模块基础设施提交可以省略范围。

## 提交前检查

1. 工作区只包含本提交目标所需的文件。
2. 新行为已经经历 RED-GREEN TDD 循环。
3. 相关 lint、类型检查、测试和构建均通过。
4. 生成代码与源文件一致，数据库迁移已被审查。
5. 不包含密钥、真实用户数据、构建产物或临时文件。

## 分支与历史

- `release-1.2.0` 只作为旧版参照，不追加 v2 提交。
- `main` 承载 Schedule v2 开发。
- 禁止对共享分支执行强制推送。
- 禁止为了整理历史而改写已经交付或已被其他工作依赖的提交。
- 合并提交、回滚提交可使用 Git 自动生成的标准形式；人工编写的说明仍优先使用中文。
